# Task MCP tool defaults: compact calls, complete evidence

**Status:** deployed through `62532ecca3587de62138eed0dc1ff843be9a681a` on 2026-10-03: package 1.0.0, protocol 7 / database schema 4. All eight candidate tasks are independently reviewed and signed off. Live migration preserved every pre-existing row and column; the configured MCP entry point and restarted viewer passed deployment checks. This conversation still has the old cached catalog and closed transport and needs a Task MCP reconnect; refreshed-host verification remains pending.

## Goal and recommendation

An agent should get enough information for the action it chose without receiving unrelated history. The tool arguments are visible to the agent, so it can request a specification or evidence in the same call when it needs them. Keep normal discovery short, return the full current specification for implementation, and fetch historical proof deliberately. The server should enforce workflow gates; tool descriptions should explain the operation, without a repeated workflow manual.

I recommend these defaults:

1. Use **title, optional authored summary, and full specification** as distinct layers. `list_tasks` and default `get_tasks(ids)` return compact cards with the title and summary, never a slice of the body. `get_tasks(ids, specification=true)` returns the full **current** specification, active gates and bounded attempt summaries. An agent that already knows it needs the specification can set the flag on its first call. `get_next_action(workstream_id)` returns the full current specification for the chosen implement/review action, plus exactly the selected attempt evidence for review. Neither call includes unrelated attempt history.
2. Add `list_task_attempts`, `get_attempt`, `list_group_members` and `withdraw_acceptance`. Review and sign-off must still retrieve the complete evidence for the chosen attempt. A full-spec read supplies the token required for a later body or criteria replacement.
3. Make write results concise acknowledgements containing affected IDs, new revisions, state/gates and new attempt/proposal IDs. The caller already supplied changed text or evidence, so the result need not echo it.
4. Bound `init` and discovery results; shorten server instructions; make the default skill-catalog request an index and allow a named request for complete skill content.
5. Change the existing tool defaults in this unreleased prototype. Reconnect agent sessions, update known callers and bump the Task MCP protocol revision. Add nullable summary fields through an explicit, data-preserving SQLite schema migration. Existing tasks remain valid without a bulk summary backfill.

## Ordinary workflows must be efficient by construction

**Agreed refinements from sign-off review — 2026-10-03.** The user should not have to teach each agent how to avoid redundant reads. Make the following part of the tool contract and its ordinary examples, not a separate mandatory workflow manual:

- Mutations use the last returned revision of the entity they change. A user pause does not invalidate that revision. The server checks it atomically; fetch and reconcile only on a conflict, an uncertain result or genuinely missing information. Tool descriptions must not imply a fresh read before every write. Task and attempt revisions must be identified explicitly in multi-entity results.
- Every write returns the affected IDs, resulting revisions and enough state to continue. This includes `record_review` and `human_review`, which still return the complete attempt in the current candidate. Do not echo specifications, submitted evidence or earlier review history. Do not require a confirming read after a successful acknowledgement.
- A scoped queue/card exposes the current applicable local attempt reference: ID, attempt revision, state and specification revision. Choose a reference relevant to its local view, and indicate alternatives without expanding their proof. This is a suggested result to inspect, not an implicit human choice or inherited approval. It must never select another workstream's proof.
- A caller that knows the task and attempt it wants can fetch the full specification and exactly that proof together using `get_tasks(ids=[...], specification=true, workstream_id=..., attempt_ids=[...])`. Validate that requested attempts belong to the requested tasks; include their actual workstream/specification provenance and never relabel old proof as current. Bound the explicit attempt batch. No card → specification → attempt-list → attempt sequence is required for ordinary review or sign-off. `get_next_action` already supplies the corresponding one-call implementation/review assignment.
- Preserve the whole-field replacement guard without forcing a read of content the caller just authored. A create acknowledgement may include the token for the complete specification supplied/defaulted by that create. An update supplied with a valid full-specification token may return the refreshed token after saving. Cards and updates without such a full-specification context must not supply a replacement token. An unchanged specification keeps its existing token. Returned revisions/tokens allow subsequent safe mutations without an intervening full read; conflicts still require reconciliation.
- Keep the packaged sign-off presentation explicit: **Asked** restates the approved goal, separately from **Built**, actual verification, fitting inspection handles, what to judge, limitations and recommendation. The local signoff skill already requires this; the Task MCP skill must retain the same fields so callers need no extra instruction.
- Verify complete ordinary workflows through real MCP calls, recording call counts and serialized response sizes. Include selection → result → review and queue → informed sign-off → verdict, with long specifications and growing historical evidence. The normal paths must need no routine read-before-write, post-write confirmation or historical expansion. Verify actual host-visible catalog size after reconnect as well as server-side result projections.

The candidate is not yet the compact-default release. `get_tasks` still expands all attempt proof, `record_review`/`human_review` still echo it, and the server instructions remain long. Complete the compact-default task before claiming that ordinary agent usage meets this goal. The user approved these refinements on 2026-10-03. The existing compact-default task now records the specification, is accepted and has its design gate resolved; implementation and independent review remain outstanding.

## Evidence and why the obvious alternative is insufficient

The raw server advertises 37 tool descriptions totaling about 3.4 thousand characters and one 1,299-character instructions string. The current client-facing catalog has 60,625 description characters: the roughly 1,301-character instructions appear in every tool description, contributing about 48,137 repeated characters. The MCP SDK passes the instructions separately, so this expansion happens in the host's presentation of the catalog. Roughly 9,000 of the remaining description characters come from parameter schemas and wrapper text; exact prompt-token cost has not been measured.

Representative serialized result sizes from the live connector, measured on 2026-10-02:

| Call/result | Size | Cause or interpretation |
| --- | ---: | --- |
| `init` on this workstream | 4,794 characters | Includes all 17 scoped queue entries. The queue is unbounded. |
| `list_tasks` for this project | 5,099 characters | 26 compact entries; already paged. |
| `workstream_status` for this workstream | 4,343 characters | 17 entries; queue is paged, though group references can grow. |
| `list_events(limit=50, include_details=false)` | 11,291 characters | Even metadata-only event history is substantial at 50. |
| `get_tasks` for six-attempt viewer task | 22,561 characters for that task | Includes 6,369 evidence characters plus superseded attempt metadata. |
| `get_tasks` for a zero-attempt design task | 6,387 characters | The current body and criteria remain large; they are useful when the specification is requested. |
| `update_task` response for a long, zero-attempt task | 9,384 characters | Echoes the complete task body. |
| `get_default_skills` | About 19,500–20,000 characters | Returns all six complete skills in one call. |

`update_task(changes={...})` already sends only the changed fields. Editing `body` sends a full replacement body; our earlier design-note append calls resent the old text plus the note. Its **response** also returns the entire task with all attempts. A compact acknowledgement fixes the response side. A body preview would make a destructive edit easy: an agent could append a note to the preview and submit it as the full body. Authored summaries remove that misleading partial body from cards, and the read-token requirement below protects whole-field replacements. Routine incremental note logging would increase calls and task-body size, so it is outside this proposal.

An offline snapshot exercise supplied with the review drafted summaries for 13 tasks across several projects. The reviewer found that roughly nine conveyed useful information beyond the title, while two added almost nothing. Many imported bodies begin with repeated ledger titles or preamble, making a fixed-length preview a poor substitute. The sample also exposed a real failure mode: first drafts described progress and priority, which are already tracked elsewhere and can change independently. A summary should state the task's intent, useful constraint or settled decision, **not** its completion state, queue position or current priority. This is an informal sample, not a measured benefit across the whole database.

Store a deliberately written, optional summary for both tasks and groups. Limit it to 240 Unicode characters, one line, with no silent truncation; reject an overlong, multiline or whitespace-only value. Omission leaves an existing summary unchanged, and an explicit null clears it. If absent, a card shows the title only, with no generated fallback or body preview. A summary is descriptive navigation text, never the source of requirements. Implementation, review and acceptance use the full body, acceptance criteria and gates returned by `specification=true`. Keep summaries current as tasks are touched rather than bulk-writing plausible descriptions for imported tasks whose bodies and status may disagree; the separate stale-import repair should resolve those contradictions before any broad backfill. Some imported bodies also repeat their acceptance criteria. That inflates full-spec reads, but silently removing source text would be a separate data edit, not a response-default change.

Cards make title quality matter more, and a summary should not compensate for a vague title. In the same sample, rewritten outcome titles closed most of the gap for four of the six tasks where a summary helped most; the summary remains for the decision, cause or constraint a title cannot hold. The packaged reference skills now ask for titles that name the observable outcome in about 70 characters with one main fact, and for bodies that contain only the specification and its open questions: progress and evidence belong in attempts, acceptance criteria in their own field, and design decisions are folded into the brief rather than appended as dated notes. Title, body and criteria are specification fields, so this applies to new tasks and edits already being made, not to bulk retitling of accepted work. Cleaning existing imported bodies (migrated checkbox lines, status logs, duplicated criteria) is a separate task because it would invalidate acceptance.

## Response contracts

**Cards — `get_tasks(ids)` and board results.** Use one card projection for `list_tasks`, default `get_tasks(ids)`, bounded `init` queues and `workstream_status` queues. Return `id`, `project_id`, `title`, optional `summary`, `summary_stale`, `object_type`, canonical disposition, task and specification revisions, current acceptance state, `specification_complete:false`, active unresolved and pending-proposal counts, prerequisite count, `selected_attempt_id` if any, and a flag/count indicating further detail. `summary_stale` is true when a stored summary's `summary_spec_revision` is older than `spec_revision`; it is null when no summary exists. A card has **no `body`, `body_preview`, `acceptance_criteria` or specification read token**. If `workstream_id` is supplied, include branch-local `view`, gate reasons and current-spec attempt counts plus the latest short local attempt summary. Without a workstream, include canonical disposition/gates and clearly labelled `aggregate_attempt_counts`; omit derived execution readiness, review and sign-off gates, because `_gate_reasons` otherwise combines attempts across branches. A caller may request up to the existing batch limit, with a bounded response per item. `list_groups` similarly returns optional group summary and freshness alongside progress.

**Specification — `get_tasks(ids, specification=true, workstream_id=...)`.** Add the complete current title/body/acceptance criteria, descriptive summary and its freshness metadata, acceptance note, active unresolved items, prerequisites and relevant parent-group context. Return pending gate proposals with their IDs, types, proposer, timestamp and full proposed detail; proposals have no separate revision, and their decision uses the task revision. Accepted/dismissed proposal decisions remain in audit history, since resolution currently deletes the proposal row. Include at most **three** current-spec attempt summaries per task: actionable states (`review`, `passed`, `human_review`) first, newest first within that tier, then the newest other states. Each summary has `attempt_id`, `attempt_revision`, `state`, `workstream_id`, `spec_revision` and a bounded summary. Return `attempt_total`, `actionable_total` and `has_more`; when more than three actionable attempts exist, the caller uses filtered `list_task_attempts` to reach the rest. An unbounded list of every actionable attempt would recreate the context problem; the count and filtered page preserve access. Preserve `selected_attempt_id` independently of that window; it is set on approval and cannot identify pre-sign-off attempts. A supplied workstream filters execution state and summaries to that workstream. An unscoped specification labels its attempt rollup cross-workstream and does not derive local readiness from it. Historical attempts and full evidence are omitted by default. Optional bounded `attempt_ids` requests add exactly the requested complete proofs to this same response, with original task/workstream/specification provenance; they do not expand unrelated history. No specification or pending-proposal text is silently truncated. For a single known task, the caller may set this flag immediately; no preliminary card call is required.

**Agreed selected action — `get_next_action(workstream_id)`.** Replace the implementation-only `get_next_task` name with a selector returning an explicit `implement` or `review` action. Follow the shared project order among eligible autonomous actions. Return the selected task's full current specification, read token, pending gate proposals and branch-local gates. For review, include exactly the selected current-spec local attempt with complete evidence, provenance and attempt revision, so the reviewer can start in one call. Pending local review takes precedence over reimplementing that task; passed/human-reviewed work waits for human sign-off, and rework supplies relevant findings. Autonomous actions require current acceptance, active disposition and clear unresolved/prerequisite gates. Exclude other-workstream and superseded results from assignments while retaining them as explicitly accessible history. When none is eligible, return `action:null` with bounded waiting diagnostics. Selection does not claim, reorder or log partial progress. This rename does not add a tool, and no compatibility alias is needed when the new surface is rolled out.

**History and proof.** Provide `list_task_attempts(task_id, workstream_id?, states?, current_spec_only=true, limit=20, cursor?)`, paged with stable ordering and IDs, implementer/provenance, state, `attempt_revision`, `spec_revision` and short summaries. `states` accepts a list, so one filtered call can page all `review`, `passed` and `human_review` attempts. The default serves current work; `current_spec_only=false` deliberately retrieves superseded attempts. Provide `get_attempt(attempt_id)` with complete evidence and review notes for exactly one attempt. Use existing paged `list_events` for audit history, with `include_details` remaining explicit. For groups, ordinary detail includes progress/counts and at most three member summaries; `list_group_members(group_id, limit=20, cursor?)` provides the complete list through paging. IDs and counts indicate when more data exists. Proof is never discarded or inferred from prose.

**Summary lifecycle and acceptance.** Add nullable `summary` and `summary_spec_revision` columns to tasks (which also store groups). Creating a task or group may supply a summary; if supplied, record the resulting `spec_revision` as its source revision. A summary-only `update_task` changes the task's ordinary `revision` and writes an audit event, but does not change `spec_revision`, acceptance or attempt state. Allow an audited summary-only correction even on a completed task or group; continue rejecting specification edits there. If a title/body/criteria edit advances `spec_revision` without a simultaneous summary edit, keep the old summary and mark it stale. If summary and specification change together, stamp the summary with the new spec revision. Supplying the same summary text on a stale task explicitly reaffirms it, updates `summary_spec_revision` and counts as `changed:true`; supplying the same text on a current task is a no-op. Clearing the summary clears its source revision. A stale summary is still visible but explicitly marked; users and agents should read the current specification before acting on it. The summary is outside the user's acceptance verdict: it is a navigational description, and acceptance continues to cover the specification and gates. A current freshness marker only means no later spec revision occurred; it cannot certify that the prose accurately describes the spec. Acceptance and sign-off screens must show the spec and proof, not ask for a verdict from the summary alone.

**Replacement-edit guard.** A full specification response includes `specification_etag`, derived from task ID, current spec revision, full `body` and full `acceptance_criteria`; the new summary columns are not part of it. Require that token as an `update_task` argument whenever `changes` contains `body` or `acceptance_criteria`, and check it against the current full specification alongside `expected_revision`. Cards and board rows never carry it. Creation from complete caller-authored specification values and updates carrying a valid full-specification token may return the resulting token in their acknowledgement, as described in the workflow refinements above. A title-only or summary-only edit needs only `expected_revision` because the card contains the complete values being edited. State clearly in the `update_task` description that `body` and `acceptance_criteria` are whole-field replacements and require a full-spec read. The token is a stale-read/data-loss guard, not authorization.

**Agreed acceptance model — 2026-10-02.** Request origin is descriptive metadata, independent of approval. `create_task` and `update_task` may carry an approval already given by the user; the service atomically saves and accepts the exact resulting specification. A concrete user request can supply that approval without another question. Without approval, creation is pending even for user-originated work, and a real specification edit becomes pending. Summary-only edits preserve acceptance. Approval does not clear other execution/review/sign-off gates. Keep `accept_task` for standalone acceptance. Add revision-checked, audited `withdraw_acceptance` for mutable tasks: reverse mistaken acceptance without dummy edits, retain prior decisions and attempt/review evidence, and prevent execution/sign-off while unaccepted. Completed work stays immutable.

**Agreed approval provenance and sign-off policy — 2026-10-02.** Approval records carry the actual supporting user instruction and a basis: `specific` for an exact-scope user request/decision, or `delegated` for real authority to select work within a stated goal. Legitimate delegated approval remains available for autonomous work. Existing acceptance without a reliable classification is `unknown`; do not guess a basis from old notes or reopen completed tasks. Sign-off presents purpose/approval basis separately from implementation evidence. A prior specific purpose decision can be shown as already answered; delegated or unknown approval needs an explicit purpose judgment at sign-off. One informed approval can cover both purpose and result, with the judgments recorded separately.

The agreed sign-off decision is one of `approve`, `rework`, `revise`, `drop` or `defer`. Approval completes accepted work only after the applicable independent or actual human review and other completion gates have passed. Rework retains the accepted requirements and sends the implementation back for repair and fresh review. Revise withdraws acceptance and adds the unresolved specification question; it preserves the reviewed result and does not advance `spec_revision` until the specification actually changes. Drop ends the work and deactivates current approval; a later revival requires real authorization. Defer pauses it while preserving approval. Both retain context and evidence and neither satisfies a prerequisite that requires completed work. Changing direction or pausing does not imply an implementation-quality judgment: record that result as not judged unless the user actually supplies a judgment. Keep the independent review distinct. Ordinary disposition changes outside reviewed-result sign-off do not require an attempt.

**Write acknowledgements.** Return affected entity IDs and revisions where the entity has a revision, status/view, acceptance and gate diagnostics, and IDs of newly created attempts, proposals or members as appropriate. `update_task` always returns `changed:true|false` and the current task/spec revisions; a no-op is `changed:false` and does not imply an edit. Recording acceptance of an unchanged pending spec is a real state transition, without changing spec revision. `record_result` returns attempt ID, revision and state without echoing submitted evidence. `record_review`/`human_review` return attempt ID/new revision, state and recorded decision without echoing evidence. `signoff_task` returns task ID/revision, current `spec_revision`, status, acceptance, decision and the relevant attempt ID/revision: approval also returns `selected_attempt_id`; `rework` returns the attempt's new state and revision; `revise` returns `accepted:false` and the newly created unresolved-item ID, with spec revision unchanged until a real specification edit; `drop` returns inactive approval and dropped status; `defer` returns deferred status with retained acceptance. Return the recorded purpose/result judgments without echoing the supplied note or evidence. Revision-conflict and gate errors remain specific enough for safe re-read and reconciliation. Specification edits without a supplied approval invalidate acceptance; explicitly approved amendments save and accept atomically.

**Discovery and catalog.** `init` returns project/workstream IDs, binding, revision, status counts and at most **10** queue cards plus total/next-page information rather than all scoped tasks. `list_workstreams` returns binding/status and scope counts by default; a deliberate scope-detail request returns the full scope through paging. `workstream_status` retains its paged queue and bounds referenced-group expansions. `list_tasks` and `list_groups` default to **20** cards and permit explicit limits up to the existing cap. `list_projects` stays compact and paged. `list_events` defaults to **20** metadata-only items, with larger explicit limits available. `get_default_skills()` returns names, versions, hashes and descriptions; `get_default_skills(name="feature-design")` returns that skill's entire content. A caller that knows the name gets it in one call.

**Agreed work-order contract — 2026-10-02.** Keep one shared project order, filtered by each workstream's scope and branch-local eligibility. Replace `reorder_tasks` whole-order replacement with an atomic move before or after a project task. Board/queue envelopes carry a concise project order revision, checked on the move; successful writes return affected IDs, the new order revision and `changed`, without resending the entire ledger. Signed-off tasks may shift position when remaining work moves without changing their requirements or proof. An already-satisfied move is a no-op. Reads and selection never reorder work, and agents should reorder only for actual scheduling intent. Evaluate excessive use after rollout through existing audit events; do not add routine reporting calls or automatic queue reshuffling. Per-workstream orders, priority fields and a cross-project scheduler are outside this agreed change.

**Agreed cross-project prerequisites — 2026-10-02.** Allow direct prerequisite links between canonical tasks in any projects, without requiring shared-group membership. Preserve cycle checks across prerequisite and implicit group-membership edges, including observer-proposal acceptance and membership changes. Diagnostics show compact blocker identity, project and blocking/completion state, without expanding remote history or changing local scope. Local and remote prerequisites retain the existing completion milestone: human-signed-off done for a task, all members done for a group. Reviewed, dropped or deferred work does not satisfy it. Evaluate that milestone after rollout through actual use; a dependency link is not proof that another branch's code was integrated.

**Agreed workstream continuation — 2026-10-02.** Resume the existing workstream identity and inspect actual checkout applicability before relying on its recorded implementation. Attempts and execution state remain local, with deliberate parallel alternatives allowed. For an open task deliberately integrated into another branch, verify the target against the current specification and record a new target-local result citing origin attempt/workstream, actual source and target commits and target verification, followed by fresh independent review. Do not inherit review or infer integration from another branch's progress. Use the existing result-recording operation rather than adding an adoption API or routine checkpoint logging. Completed tasks retain their selected human-approved result; new integration requirements after completion are new tasks.

**Agreed factual result recording — 2026-10-02.** `record_result` records actual durable implementation and verification evidence even if acceptance, unresolved or prerequisite gates remain. Keep revision checking, the checked specification and workstream/implementer provenance, concrete evidence, mutable-task and project/scope checks. It creates an unreviewed attempt and leaves acceptance, disposition and other gates intact; deferred/dropped work is not resumed, completed work remains immutable, and groups have no attempts. A concise acknowledgement includes the attempt ID/revision and remaining acceptance/disposition/blockers rather than echoing evidence. Factual recording neither authorizes new implementation nor supplies independent review, human approval or prerequisite completion. Keep one durable result per finished attempt without routine start, heartbeat or checkpoint calls. The user also approved next-action selection and automatic resumption of eligible local review, as described above.

Every Store-backed read currently writes an audit event. Fetching a card, then a specification, then an attempt list and then an attempt therefore adds calls **and** audit rows. The intended paths are one full-spec call when implementation or review is already intended, one `get_next_action` call to select implementation or obtain a complete review assignment, and a single `get_attempt` when deliberately inspecting a known attempt; a card-first sequence is for discovery only. Keep the extra history calls optional rather than making every workflow traverse them.

## Safety, implementation boundary and verification

**Rollout authorization — 2026-10-03.** The user reported that no other agents are running and authorized sign-off followed by deployment, clearing the temporary 2026-10-02 compatibility hold. Keep production unchanged until compact defaults pass independent review and receive their informed human verdict. Then take a fresh verified online database backup, switch the approved candidate and prepared companions, migrate safely, restart serving processes and verify the actual client runtime/catalog. No permanent legacy API layer is required.

The response-shape change belongs primarily at the MCP surface. Keep `Store.get_tasks` and the viewer's `details` route capable of serving full detail. The browser currently calls `Store.get_tasks` directly through its local HTTP allowlist, so an MCP projection can leave its detail view intact. Add summary and freshness to the viewer's task and group lists, with a visible stale indicator and full-spec access for editing. The summary requires a narrow database change; keep task/spec/attempt revision semantics, acceptance, prerequisites, independent review, sign-off, audit and truthful tool annotations. A client can see the parameters it sent, but the service cannot authenticate a human decision; concise responses must never pretend otherwise.

Change the current `Store._revision` error for task edits: it says to call `get_tasks` after a conflict. With card defaults that is insufficient for reconciling a body replacement. The MCP error should direct callers to `get_tasks(ids=[task_id], specification=true)` before retrying a body/criteria edit; the Store-level wording should similarly say to re-read the **full specification**, then reconcile against the new revision and read token. A summary-only edit can reconcile from a fresh card. Attempt conflicts should direct callers to `get_attempt(attempt_id)` when full evidence/review notes matter, or a current `list_task_attempts` row when only state/revision is needed. Test the conflict path with a long body so a card cannot become a replacement.
